# Касса в портале: уведомления о движении наличных и перевод между кассами

Дата: 2026-11-06. Статус: черновик на утверждение.

## Зачем

Сейчас при оплате наличной заявки портал дёргает в n8n вебхук `new-payed-request`, а n8n:

1. при «Перевод между кассами» создаёт приход в кассе-получателе (`POST /api/n8n/cash/revenues/`, кассу берёт регэкспом из строки «В кассу: …» в описании);
2. шлёт в кассовую Telegram-группу сообщение «Движение денежных средств» с остатками касс.

Кассир нажимает «Выплатить» и не заходит в портал: по сообщению в группе он видит, что выплата прошла, и сверяет остаток с наличными на руках. Это чисто информационное сообщение.

В n8n это сделано по-разному у каждого тенанта и местами сломано:

- **LemonAqua** — сообщения о расходе не уходят совсем: узел берёт остатки у Lemonfit, ищет кассу Aqua (`wallet_id=14`) и падает (ошибки в n8n, например заявки 9032, 8973, 8924).
- **Lemonfit NEW** — сообщения не уходят совсем: все наличные заявки NEW имеют тип «Инвест. наличные», а проверка в n8n требует ровно «Наличные» (приставку «Инвест. » снимает только HAVO). Кассовой группы NEW (`-5457282029`) нет в портале.
- **NeuronMed** — другой формат: одна касса «Основная» (`wallet_id=11` зашит), без списка остатков; у всех наличных заявок Neuron касса не указана, поэтому расход из долларовой кассы показывался бы с остатком сумовой.
- **Qulay** — о расходах не сообщается вообще; «Наличные с банка» обрабатывается в n8n своей кнопкой «Подтвердить» (модуль портала «Снятие наличных» для Qulay не настроен). В отключённых узлах workflow Qulay открытым текстом лежат логин/пароль API Капиталбанка и integration-token Aqua.
- Перевод между кассами держится на регэкспе по тексту (уже ломался: HAVO, заявка 8907).

Цель — перенести это в портал, одинаково для всех тенантов, и отключить соответствующие узлы n8n сразу после выкладки, без переходного периода.

## Цели

- Одно правило для всех тенантов с наличными (lemonfit, lemonaqua, lemonhavo, lemonnew, neuron, qulay). Различие между тенантами — только в настройке (какая группа кассовая, включено ли).
- Формат сообщения — как сейчас у Lemonfit (у него есть вся нужная информация), плюс строка с кассой и выделение затронутых касс.
- Перевод между кассами создаёт приход в кассе-получателе по структурной ссылке, а не по тексту.
- После выкладки — один список: какие узлы n8n у какого тенанта отключить.

## Не цели

- Google Sheets (выгрузка «Расходы ДС с заявок») остаётся в n8n.
- Дивиденды (`/api/n8n/investments/returns/portal-create/`) — следующий отдельный шаг.
- Neuron: пополнение корпоративной карты, ветки «Бонусы врачам» / «Выдача наличных (зарплата)» в n8n (уже обрабатываются модулем «Снятие наличных» в портале), Kapitalbank-вызовы Qulay (отключены) — не трогаем.
- Kolberg Production (kp) — касс нет, его не касается.
- Необязательные дополнения (кнопка «Открыть заявку», строка «кто выплатил», сообщения о поступлениях) — не сейчас. Решение автора, можно добавить потом.

## Анти-цели (провал, даже если «работает»)

- Сообщение уходит дважды (портал + n8n, или повторно на одну заявку).
- Приход по переводу задваивается (в том числе с приходами, которые уже создал n8n с тем же `external_id`).
- Остатки в сообщении расходятся с порталом (взяты до записи прихода/расхода).
- Тихие ошибки: приход не создан или сообщение не ушло, и об этом нигде не видно.
- Сбой модуля ломает оплату заявки.

## Как устроено

### Новый модуль `cash_desk` (`backend_v2/apps/modules/cash_desk/`)

Отдельный модуль по образцу `cash_withdrawals` (ничего в рабочих модулях не переписываем — OCP). Регистрирует обработчик оплаты через `requests.status_events.register_request_payed_event_handler` в `AppConfig.ready()`.

**Настройка** — модель `CashDeskConfig` (OneToOne tenant): `is_active`, `telegram_chat` (FK `telegram_approvals.TenantTelegramChat`, nullable), `updated_at/updated_by`. API `GET/PUT /api/cash-desk/config/` (права `IsTenantAdminOrDirector`, как у `cash_withdrawals`), отдаёт список активных чатов тенанта для выбора.

- Нет конфига или `is_active = false` → модуль для тенанта не делает **ничего** (ни прихода по переводу, ни сообщения). Это и есть переключатель «касса в портале» на тенанта: его включают в момент отключения узлов n8n, поэтому портал и n8n никогда не создают приход одновременно.
- `is_active = true`, но чат не выбран или неактивен → приход по переводу создаётся, сообщение не отправляется (`logger.warning`).

> Решение автора: один флаг на тенанта вместо отдельного флага для прихода. Окно между включением в портале и отключением n8n — минуты, в это время возможен дубль сообщения; приход не задвоится: n8n шлёт upsert без `source_year`, `N8nCashRevenueUpsertView` находит запись по `(tenant, external_id)` и обновляет её, а не создаёт новую.

**Журнал сообщений** — модель `CashDeskMessage`: `request` (FK, unique — одно сообщение на заявку), `telegram_message` (OneToOne `telegram_approvals.TelegramMessage`, nullable), `status` (`sent` / `failed`), `error` (text), `created_at`. Строка создаётся до отправки (в транзакции оплаты) — она и есть защита от повтора; после отправки заполняются `telegram_message`/`status`. Видна в Django admin.

### Обработчик оплаты

Срабатывает, если `canonical_payment_type(request.payment_type) == "Наличные"` (то есть и «Наличные», и «Инвест. наличные»). Обработчик сам оборачивает работу в `transaction.atomic()` (диспетчер payed-событий не делает savepoint), исключения логирует, оплату не роняет.

1. **Перевод между кассами** (`payment_purpose == "Перевод между кассами"`, константа уже есть в `investments/funding_pool.py`): создать подтверждённый `CashRevenue` в кассе-получателе.
   - `external_id = f"cash-{request.id}"`, `source_year` — год по Ташкенту (в проде колонка NOT NULL), `created_by` — системный пользователь pk=1, `operation = f"Перевод между кассами {title}"`, `comment = description`, `currency = to_wallet.currency`, `total_sum = target.to_amount`, `revenue_at = now`, `payload = {"source": "cash_desk_transfer", "request_id": ...}`.
   - Дедуп: если `CashRevenue(tenant, external_id=cash-<id>)` уже есть (создал n8n раньше) — не создавать.
   - Касса-получатель: из `CashRegisterTransferTarget` (см. ниже); если её нет (старые заявки, созданные до выкладки) — один раз парсим «В кассу: <имя> (<CUR>)» из описания и ищем `CashRegister` тенанта по имени (обрезка пробелов, без учёта регистра; суффикс «(CUR)» отрезать); сумма — `request.amount`, только если валюта найденной кассы совпадает с валютой заявки. Не нашли / нашли несколько / валюты различаются → приход не создаётся, `logger.error` с id заявки, в журнале сообщения отметка об ошибке; сообщение всё равно уходит (без строки «В кассу»).
2. **Сообщение**: в `transaction.on_commit` — чтобы остатки считались после записи расхода и прихода.

### Структурная касса-получатель перевода

Новая модель в `cash_desk`: `CashRegisterTransferTarget` — `request` (OneToOne), `to_wallet` (FK `wallets.Wallet`, тип cash, того же тенанта), `to_amount` (Decimal, > 0) — **сумма зачисления** в валюте кассы-получателя. Модель `Request` не меняем.

API: `PUT /api/cash-desk/transfers/<request_id>/target/` `{to_wallet_id, to_amount?}` — для заявки в статусе DRAFT с назначением «Перевод между кассами», кассой того же тенанта, отличной от источника (`wallet_ref`). Если валюты касс совпадают — `to_amount` не обязателен и сохраняется равным `request.amount` (передан другой → 400). Если различаются — `to_amount` обязателен. Права — тот, кто может редактировать заявку.

Фронтенд: `frontend_v2/src/lib/cashRegisterTransfer.ts` после создания черновика и **до** `submitRequestForApproval` вызывает этот эндпоинт (обе формы — `CashRegisterTransferButton.tsx` и Telegram-страница `TgCashRegisterTransferPage.tsx` — идут через эту функцию). Если выбраны кассы разных валют, в обеих формах вместо нынешнего предупреждения «уточните сумму зачисления в примечании» появляется обязательное поле **«Сумма зачисления (<валюта получателя>)»**; в описание добавляется строка «Сумма зачисления: <сумма> <CUR>». Текст «Из кассы / В кассу» оставляем как есть (его читают люди). Сейчас поля формы `from_wallet_id/to_wallet_id` содержат `CashRegister.id` — в эндпоинт передаём wallet id кассы (как уже делается для `wallet_ref`).

Разновалютных переводов в проде пока не было ни одного (90 переводов, все в одной валюте) — решение пользователя: оставить возможность через поле «сумма зачисления», а не запрещать.

### Касса расхода и остатки

- **Касса, из которой ушли деньги** = `CashExpense(tenant, external_id="req-<id>").wallet` — портал создаёт этот расход при оплате (режим `create`; по проду с 1 октября так у 100 % наличных заявок всех тенантов) и уже выбирает кассу: `wallet_ref`, иначе касса по умолчанию для валюты. Это закрывает «Инвест. наличные» — для них портал ставит инвест-кассу сам. Если расхода нет (режим `callback`) — `resolve_wallet_for_cash(wallet_ref или по валюте)`, с `logger.warning`.
- **Остатки** = `wallets.services.balances_for_tenant_channel(tenant_id, CASH)`, только активные кассы (`anchor_is_active`), в порядке, который отдаёт функция. Это тот же расчёт, что видит n8n сейчас через `/api/n8n/wallet-balances/?channel=cash`.

### Формат сообщения (HTML, как Lemonfit)

```
💰 <b>Движение денежных средств</b>

🆔 <b>ID:</b> 9032
📅 <b>Дата:</b> 06.11.2026
🔄 <b>Вид движения:</b> Расход            ← «Перемещение» для перевода
🏦 <b>Касса:</b> Основная касса           ← для перевода: «Из кассы → В кассу»

💵 <b>Сумма:</b> <code>1 500 000 UZS</code>
💱 <b>Зачислено:</b> <code>120 USD</code>   ← только для перевода между кассами разных валют

📝 <b>Назначение платежа:</b>
Ремонтные работы
👤 <b>Получатель:</b> …                    ← «—», если пусто
💬 <b>Комментарий:</b>
…                                          ← «—», если пусто

💳 <b>Категория:</b> …
🏢 <b>Плательщик:</b> …

📊 <b>Остатки по всем кассам:</b>
👉 <b>Основная касса: 12 300 000 UZS</b>   ← затронутые кассы выделены
🏦 Сейф: 40 000 000 UZS
```

Дата — `payed_at` (fallback `billing_date`), формат `dd.mm.yyyy` (`cash_withdrawals.formatter.format_payed_date`). Деньги — `format_money`. Имена касс — `wallet_label` (без «(касса)»). Все пользовательские значения экранируются (`html.escape`). Точный значок выделения — на усмотрение исполнителя.

Отправка — `TelegramDispatcher(tenant).send(action=get_requests_messaging_gateway_settings(tenant).send_action, recipient_id=chat.chat_id, text=..., request_id=...)`; шлюз по умолчанию шлёт HTML. Бот — бот тенанта в портале.

## Выкладка и отключение n8n

После деплоя (до отключения n8n) по каждому тенанту в портале:

| Тенант | Кассовая группа в портале | Что сделать |
|---|---|---|
| lemonfit | «Касса LemonFit One» | включить, выбрать группу |
| lemonaqua | «Касса AQUA» | включить, выбрать группу |
| lemonhavo | «Касса HAVO» | включить, выбрать группу |
| lemonnew | нет | добавить группу `-5457282029` в чаты тенанта, пригласить бота портала, включить |
| neuron | «NM - касса» | включить, выбрать группу |
| qulay | «QULAY BOX buxgalteriyasi» (в эту группу шлёт n8n) | проверить, что бот портала в группе; включить |

В группы Lemonfit/Aqua/HAVO/Neuron бот портала уже пишет карточки «Снятие наличных», в Qulay/NEW — проверить.

Миграция данных модуля заранее создаёт недостающую группу NEW (`-5457282029`, «Касса NEW») и для всех шести тенантов — выключенный `CashDeskConfig` с выбранной группой из таблицы (существующие группы и настройки не трогает). Пользователю остаётся только включить «Касса» у тенанта в момент отключения n8n.

**Qulay, «Наличные с банка»** — только настройка модуля «Снятие наличных» (без кода): правило `Перечисление / Наличные с банка → Основная (UZS)`, группа карточек «QULAY BOX buxgalteriyasi», подтверждающие — кого назовёт пользователь.

**Узлы n8n к отключению** (в n8n отключённый узел пропускает данные дальше, поэтому отключаем конечные узлы, а не «Wait»; после правки — опубликовать):

- lemonfit (`5fl9ikv21LDYVCYf`), lemonaqua (`H28GTdJEz5cmM2cy`), lemonhavo (`V8Ty0LXIrIVSETku`), lemonnew (`MTHSUG2ZrVularMf`): `HTTP Cash Revenue1`, `Send Cash Notification1`, `Send Cash Notification2`.
- neuron (`pDYShuaYC6xbggnH`): `Send a text message`.
- qulay (`gPgbNdVRYQBno4rr`): `Send message and wait for response`, `HTTP Request3`, `Send a text message1` — после настройки «Снятия наличных» для Qulay.
- Безопасность: из workflow Qulay удалить отключённые узлы `Call 'Kapitalbank'`, `Call 'Kapitalbank'1`, `Request set expense id`, `Request set expense id1` (пароль Капиталбанка и токен Aqua открытым текстом), затем сменить этот пароль и перевыпустить токен интеграции Aqua.

Финальный список исполнитель сверяет с актуальными workflow через n8n API (`~/.config/n8n-api/api_key`) перед тем, как отдать пользователю.

## Тесты (CI, локально не запускать)

- Расход «Наличные» и «Инвест. наличные» → одно сообщение в группу, касса из `CashExpense`, остатки после списания.
- Перевод с `CashRegisterTransferTarget` → приход в кассе-получателе, сообщение «Перемещение», обе кассы выделены.
- Перевод без target, но с «В кассу: X (UZS)» → приход по имени; с неизвестным именем → прихода нет, ошибка в журнале, оплата не падает.
- Уже существующий `CashRevenue cash-<id>` → второй не создаётся.
- Повторный вызов обработчика → второе сообщение не уходит.
- Модуль выключен → ни прихода, ни сообщения. Включён без чата → приход создаётся, сообщения нет.
- Ошибка отправки в Telegram → `status=failed`, оплата успешна.
- Экранирование HTML в описании/получателе.
- Разновалютный перевод: приход в валюте получателя на `to_amount`, строка «Зачислено» в сообщении; без `to_amount` → 400; старая заявка без target с разными валютами → прихода нет, ошибка в журнале.
- API target: чужая касса, касса-источник, не DRAFT, не перевод → 400/403; одна валюта и `to_amount ≠ amount` → 400.
- Vitest: `cashRegisterTransfer` вызывает эндпоинт target до submit и передаёт `to_amount` только для разных валют; поле «Сумма зачисления» появляется и обязательно только при разных валютах.
